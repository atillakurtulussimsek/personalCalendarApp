# Architecture

## Overview

```
 Android (Flutter) ─┐                          ┌─ MySQL 8
                    ├─ HTTPS ─ Go API (chi) ───┤
 macOS (Flutter) ───┘        self-hosted       └─ (phase 5) FCM / WebSocket fan-out
```

* Single Go binary, stateless, migrations embedded and applied at boot.
* Clients own their data locally (drift/SQLite) and talk to the server only through
  `/sync` for data and the REST resources for convenience/admin operations.
* All timestamps are stored and transmitted in UTC (RFC 3339). Events additionally
  carry an IANA `timezone` used for recurrence expansion.

## Data model

Every syncable table (`calendars`, `events`, `notes`) has:

| column       | purpose                                                        |
|--------------|----------------------------------------------------------------|
| `id`         | UUID generated by the client (offline creation)                |
| `user_id`    | owner                                                          |
| `created_at` / `updated_at` | UTC; `updated_at` is the last-writer-wins clock |
| `deleted_at` | soft delete → tombstone is synced, never purged (phase 6 may add GC) |
| `version`    | per-record counter, +1 on each server-side write               |
| `server_seq` | global, monotonic, assigned on each write; drives incremental pull |

Exception instances of a recurring event are rows with `recurrence_id` (= master id)
and `original_start` (= the occurrence they replace). A deleted exception row is a
"cancelled occurrence".

## Sync protocol

### Pull — `GET /sync?since=<seq>&limit=<n>`

Returns every calendar/event/note of the user with `server_seq > since`, including
tombstones, ordered by `server_seq`, plus `last_seq` and `has_more`.

Pagination is safe across entities: if any entity hits `limit`, the page is cut at the
smallest "full" sequence so that no row of another entity is skipped. The client stores
`last_seq` and repeats until `has_more` is false.

### Push — `POST /sync`

```json
{ "items": [
  { "entity": "note", "op": "upsert", "id": "…", "base_version": 2,
    "updated_at": "2026-02-01T09:03:00Z", "data": { "title": "…", "body": "…", "tags": [] } },
  { "entity": "event", "op": "delete", "id": "…", "base_version": 1,
    "updated_at": "2026-02-01T09:04:00Z" }
]}
```

Each item is applied in its own transaction and answered individually:

| status     | meaning                                                                 |
|------------|-------------------------------------------------------------------------|
| `applied`  | written; `version`/`server_seq` are the new values                       |
| `conflict` | server version kept; `current` carries the server record                 |
| `rejected` | validation failure; `error` explains (client should fix or drop the item) |
| `ignored`  | no-op, e.g. delete of a record the server never saw                      |

Conflict resolution (`base_version` ≠ server `version`):

1. **Last writer wins** on `updated_at`: the pushed item is applied only if its
   `updated_at` is strictly newer than the server's.
2. **Notes never lose text.** Whenever a real conflict involves a different `body`,
   the losing body is stored as a new note titled `(çakışan kopya) <title>` and its id
   is returned as `conflict_copy_id`. This applies in all three cases: server wins,
   client wins, and a stale delete that overwrote a newer server edit.
3. Events and calendars use plain LWW (no copies).

### Client algorithm (phase 2)

1. Every local write → local DB + outbox row (collapse multiple edits of the same record).
2. Sync run: push outbox → handle results (`conflict` ⇒ overwrite local with `current`,
   `rejected` ⇒ surface to the user) → pull since `last_seq` → apply → reschedule reminders.
3. Triggered on app foreground, connectivity regain, periodic (WorkManager), and in
   phase 5 by a server push signal.

## Recurrence

`GET /events?from&to&expand=true` expands RRULEs server-side with `teambition/rrule-go`
in the event's own timezone (local wall time is preserved across DST), applies exception
rows, and returns `occurrences` with `occurrence_start`/`occurrence_end`, `series_id` and
`is_exception`. Without `expand` the raw rows (masters + exceptions + singles) overlapping
the range are returned.

## Auth

* Password: argon2id (m=19 MiB, t=2, p=1), PHC string.
* Access token: HS256 JWT, 15 min, `sub` = user id, `did` = device id.
* Refresh token: 32 random bytes, stored as sha256 in `sessions`, rotated on every
  `/auth/refresh`; one live session per device; `/auth/logout` revokes.
* Registration can be closed with `ALLOW_REGISTRATION=false`.

## Error format

```json
{ "error": { "code": "validation_error", "message": "end_at must not be before start_at" } }
```

Codes: `bad_request`, `validation_error`, `unauthorized`, `forbidden`, `not_found`,
`conflict`, `version_conflict`, `method_not_allowed`, `internal_error`. Rate limiting
answers `429 Too Many Requests`.
